# 합성과 유연한 설계
상속, 합성은 객체지향에서 널리 사용되는 코드 재사용 기법임.

합성 : 전체를 표현하는 객체가 부분 표현하는 객체를 포함해서 부분 객체의 코드를 재사용함.

합성: 두 클래스 간의 의존성은 런타임에서 해결된다.

상속관계 : is-a관계
합성관계 : has-a관계

합성은 구현에 의존하지 않는다는 점에서 상속과 다르다. 합성은 내부에 포함되는 객체의 구현이 아닌 퍼블릭 인터페이스에 의존한다. 
합성을 이용하면 포함된 객체의 내부 구현이 달라지더라 영향을 최소화할 수 있다. 

상속은 정적인 관계이지만, 합성은 실행시점에 바뀔 수 있는 동적인 관계이다.

> 코드 재사용을 위해서는 객체 합성이 객체 상속보다 더 좋은 방법이다.

상속 : 화이트박스 제사용
합성: 블랙박스 재사용

## 01 상속을 합성으로 변경하기
상속 사용시 안 좋은 점 
- 불필요한 인터페이스 상속 문제
- 메서드 오버라이딩의 오작용 문제
- 부모클래스와 자식클래스의 동시 수정 문제

### 메서드 오버라이딩의 오작용 문제
인터페이스를 상속받고, 내가 재사용하고 싶은 코드를 포워딩 메서드로서 사용하자. 
재정의 하고 싶은 것만 재정의해서 사용하자.
```java
class A {
    public void someMethod() {
        System.out.println("A's method");
    }
}

class B {
    private A a = new A();

    public void someMethod() {
        a.someMethod(); // 포워딩 메서드
    }
}
```

## 03 합성 관계로 변경하기
상속은 컴파일 타임에 결정되기 때문에 -> 클래스 폭발 문제가 야기된다. 
합성은 컴파일 타임을 런타임으로 변경하면서 문제 해결한다.

컴파일 의존성과 런타임 의존성이 달라질수록 이해하기 어려워지는건 맞으나, 변경에는 유연하게 동작할 수 있다.

### 기본 정책 합성하기
각 정책을 별도의 클래스로 구현한다.

- RatePolicy interface를 추가한다.
- 인터페이스 상속받는 BasicRatePolicy 추상 클래스를 만든다. 
- 이제 이것들을 상속받는 regular, night 요금제를 만든다.
- 이제 요금제를 사용해 요금 계산을 할 수 있도록 phone을 만든다.
```java
public class phone{
    private RatePolicy ratePolicy;
    private List<Call> calls = new ArrayList<>();
```

## 04 믹스인 (상속 + 합성)
믹스인 : 객체를 생성할 때 코드 일부를 클래스 안에 섞어 넣어 재사용하는 방법. 합성이 런타임 시점에 객체를 조합하는 방법이라면
믹스인은 컴파일 시점에 필요한 코드 조각을 조합하는 재사용 방법이다.

상속의 진정한 목적은 자식 클래스를 부모 클래스와 동일한 개념적인 범주로 묶어 is-a 관계를 만들기 위한 것이다. 
믹스인은 코드를 다른 코드 안에 섞어 넣기 위한 방법이다.
