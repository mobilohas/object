# 01 다형성

다형성(Polymorphism): 하나의 추상 인터페이스에 대해 코드를 작성하고 이 추상 인터페이스에 대해 서로 다른 구현을 연결할 수 있는 능력

- Universal(유니버설) 다형성
    - Parametric(매개변수): 인스턴스 변수 또는 paramter 타입을 임의 타입으로 선언한 후 사용 시점에 구체적 타입으로 지정하는 방식(제네릭)
    - Inclusion(포함): 메시지가 동일하더라도 수신한 객체 타입에 따라 수행되는 행동이 달라지는 능력(subtype 다형성)
- Ad Hoc(임시) 다형성
    - Overloading(오버로딩): 하나의 클래스 내에 동일한 이름의 메서드가 존재하는 경우
    - Coercion(강제): 타입 변환을 이용해 동일 연산자를 다양한 타입에 사용하는 방식

# 02 상속의 양면성

상속의 목적은 코드 재사용이 아닌 다형성을 위한 타입 계층 구축

## 상속을 사용한 강의 평가

- 메서드 오버라이딩: 상속받은 메서드와 동일한 시그니처의 메서드 재정의해서 부모 클래스의 구현을 대체하는 것
- 메서드 오버로딩: 부모 클래스의 메서드와 이름은 같지만 시그니처는 다른 메서드를 자식 클래스에 추가하는 것

## 데이터 관점의 상속

데이터 관점에서, 상속은 자식 클래스 인스턴스 안에 부모 클래스 인스턴스 포함하는 것

- 자식 클래스는 부모 클래스 내 모든 인스턴스 변수를 포함하게 된다

## 행동 관점의 상속

행동 관점에서, 상속은 부모 클래스가 정의한 일부 메서드를 자식 클래스에 포함시키는 것

- 외부 객체가 부모 클래스 인스턴스에 전송할 수 있는 모든 메시지는 자식 클래스 인스턴스에게도 전송할 수 있다

상속 관계 메서드 탐색: 런타임에 자식 클래스에 정의되지 않은 메서드를 부모 클래스에서 탐색

- 인스턴스 변수 → 인스턴스 → 클래스 → 부모 클래스 참조
- 메시지 수신한 객체는 자신의 클래스에서 메서드 찾은 후 포인터를 따라 부모 클래스 차례로 탐색

# 03 업캐스팅과 동적 바인딩

## 같은 메시지, 다른 메서드

참조 타입과 무관하게 실제 메시지 수신 객체 타입에 따라 메서드가 달라지는 것은 업캐스팅, 동적 바인딩 때문

- 업캐스팅: 부모 클래스 타입 변수에 자식 클래스 인스턴스 할당할 수 있게 하는 메커니즘
- 동적 바인딩: 메시지 처리할 메서드를 컴파일 타임이 아닌 실행 시점에 결정하게 하는 메커니즘

업캐스팅, 동적 바인딩은 코드 변경 없이 기능 추가 가능하게 해줌 → 개방-폐쇄 원칙 의도와 일치

## 업캐스팅

컴파일러 관점에서 자식 클래스는 제약 없이 부모 클래스 대체 가능

→ 부모 클래스와 협력하는 클래스는 다양한 자식 클래스와 협력 가능(앞으로 추가될 자식 클래스 포함)

→ 확장 가능성

## 동적 바인딩

- 정적 바인딩, 초기 바인딩, 컴파일타임 바인딩: 호출할 함수를 컴파일타임에 결정하는 방식
- 동적 바인딩, 지연 바인딩: 실행될 메서드를 런타임에 결정하는 방식

# 04 동적 메서드 탐색과 다형성

self(this) 참조

- 객체 메시지 수신 시 self(this) 라는 임시 변수 생성 후 수신 객체 가리키도록 설정
- 동적 메서드 탐색은 self에서 시작해 상속 계층 역방향으로 이뤄짐
- 메서드 탐색 종료 후 자동 소멸

동적 메서드 탐색의 두 가지 원리

- 자동적인 메시지 위임: 클래스 사이의 위임은 프로그래머 개입 없이 상속 계층 따라 자동으로 이뤄짐
- 동적인 문맥: self 참조 타입에 따라 메서드 탐색 문맥이 동적으로 결정

## 자동적인 메시지 위임

메시지는 상속 계층을 따라 부모 클래스에게 자동으로 위임

- 상속 계층 정의 = 메서드 탐색 경로 정의

### 메서드 오버라이딩

자식 → 부모 방향으로 메서드 탐색

→ 자식 클래스가 부모 클래스 메서드 오버라이딩할 경우 자식 클래스 메서드가 부모 클래스 메서드 감춤

### 메서드 오버로딩

시그니처가 다르므로 동일한 이름의 메서드 공존

- C++의 경우 부모 클래스의 같은 이름 메서드 전체를 숨김 (name hiding)

*동적 메서드 탐색 규칙은 언어마다 다르다*

## 동적인 문맥

부모 class에서 self 참조에 메시지 전송하면 메시지 수신한 자식 class부터 메서드 탐색

- self가 메시지 처음 수신한 인스턴스 가리키기 때문

→ self 전송이 깊은 상속 계층 + 메서드 오버라이딩과 만나면 이해하기 어려운 코드가 만들어진다

## 이해할 수 없는 메시지

이해할 수 없는 메시지 = 최상위 클래스까지 탐색해도 처리할 수 없는 메시지

### 정적 타입 언어와 이해할 수 없는 메시지

상속 계층 전체 탐색 후에도 처리하지 못하면 컴파일 에러

### 동적 타입 언어와 이해할 수 없는 메시지

실제 코드 실행 전에는 메시지 처리 가능 여부 판단할 수 없음

몇 가지 동적 언어는 self 참조에 메서드 처리 할 수 없다는 메시지 전송

→ 해당 메시지에 응답할 수 있는 메서드 구현할 수 있다

- 메시지 선언된 인터페이스와 메서드 정의된 구현 분리
- 자율적인 객체, 유연성 → 코드 이해하고 수정하기 어렵게 만들고 디버깅 복잡
    - 정적 타입 언어는 유연성 부족하지만 안정적

## self 대 super

- self 전송 - 메시지 수신 객체의 클래스에 따라 메서드 탐색 시작 위치 동적으로 결정
- super 전송 - 항상 메시지 전송 객체의 부모 클래스에서부터 메서드 탐색 시작

# 05 상속 대 위임

상속을 자식 클래스에서 부모 클래스로 self 참조 전달하는 메커니즘으로 바라볼 수 있다

## 위임과 self 참조

위임: 자신이 수신한 메시지를 다른 객체에게 동일하게 전달해서 처리 요청하는 것

- 포워딩은 self 참조 전달 X, 위임은 self 참조 전달 O
- 상속 사용하면 위임이 자동으로 처리
- self 참조 전달은 자식 클래스 인스턴스 - 부모 클래스 인스턴스가 동일한 실행 문맥 공유하게 해줌

## 프로토타입 기반의 객체지향 언어

클래스 기반: 클래스 사이의 메시지 위임 자동 처리

프로토타입 기반: 객체 사이의 메시지 위임 자동 처리

- 정적인 클래스 간 관계 아닌 동적인 객체 사이의 위임을 통해 상속 구현
- javascript는 prototype으로 연결된 객체 체인 거슬러 올라가며 자동으로 객체간 메시지 위임 처리

*상속은 단지 클래스 사이의 정적인 관계로만 구현되는 것이 아니다*
