상속을 사용하는 두 용도

- 타입 계층 구현
    - 부모 클래스는 자식 클래스의 일반화, 자식 클래스는 부모 클래스의 특수화
    - 다형적 관계 → 확장 가능, 유연
- 코드 재사용
    - 강결합으로 인해 설계 변화, 진화 방해

다형적 객체를 위해서는 객체 행동 기반으로 타입 계층 구성해야 한다

# 01 타입

## 개념 관점의 타입

사물 분류를 위해 우리가 인식하는 객체들에 적용하는 개념, 아이디어

- 인스턴스(객체): 타입 개념이 적용되어 분류되는 대상

타입의 구성 요소

- 심볼: 타입의 이름
- 내연: 타입에 속하는 객체들의 공통적 속성, 행동의 집합
- 외연: 타입에 속하는 객체들의 집합

## 프로그래밍 언어 관점의 타입

비트 묶음에 의미를 부여하기 위해 정의된 제약과 규칙

목적: 코드 의미 명확하게 전달, 개발자의 실수 방지

- 타입에 수행될 수 있는 오퍼레이션 집합 정의
- 타입에 수행되는 오퍼레이션에 대해 약속된 문맥 제공

## 객체지향 패러다임 관점의 타입

퍼블릭 인터페이스가 타입을 결정, 동일한 인터페이스를 가지면 동일한 타입

- 프로그래밍 언어 관점: 객체가 수신할 수 있는 메시지의 종류(퍼블릭 인터페이스)를 정의하는 것
- 개념 관점: 수신 가능한 메시지로 객체들을 분류하기 위한 기준

객체의 타입은 속성이 아닌 행동으로 결정된다

# 02 타입 계층

## 타입 사이의 포함관계

슈퍼타입: 두 타입 관계에서 더 일반적인 타입

- 다른 집합의 모든 멤버를 포함하는 집합(superset)
- 내연이 더 일반적으로 정의됨(일반화)

서브타입: 두 타입 관계에서 더 구체적인 타입

- 더 큰 집합에 포함되는 집합(subset)
- 내연이 더 구체적으로 정의됨(특수화)

## 객체지향 프로그래밍과 타입 계층

퍼블릭 인터페이스 관점의 슈퍼타입, 서브타입

- 슈퍼타입: 서브타입이 정의한 퍼블릭 인터페이스를 일반화시켜 더 범용적으로 정의한 것
- 서브타입: 슈퍼타입이 정의한 퍼블릭 인터페이스를 특수화시켜 더 구체적으로 정의한 것

서브타입의 인스턴스는 슈퍼타입의 인스턴스로 간주될 수 있다(부분집합)

# 03 서브클래싱과 서브타이핑

## 언제 상속을 사용해야 하는가?

두 질문에 ‘예’라고 답할 수 있는 경우에만 상속 사용하라(마틴 오더스키)

- 상속 관계가 is-a 관계를 모델링하는가?
    - `[자식클래스]는 [부모클래스]다` 라고 말해도 이상하지 않은가
- 클라이언트 입장에서 부모 클래스의 타입으로 자식 클래스를 사용해도 무방한가?
    - 행동 호환성: 클라이언트가 부모와 자식 클래스 차이를 몰라야 한다

## is-a 관계

is-a 보다 행동 호환성이 더 중요하다

- 어휘적으로만 접근하면 혼란을 초래할 수 있다
    - ex) 펭귄은 새다, 새는 날 수 있다 → 펭귄은 사실 날 수 없음
- 타입 계층의 의미는 행동이라는 문맥에 따라 달라질 수 있다
    - ex) 새가 날길 요구하는 어플리케이션이라면 no, 새가 그저 울면 되는 어플리케이션이라면 ok
- is-a 관계는 상속 사용할 후보 정도로 생각하라

## 행동 호환성

행동 호환 여부 판단 기준 = 클라이언트의 관점

- 클라이언트가 두 타입에 대해 동일하게 행동하기를 기대하는가

다르게 행동하는 상속관계를 유지하려 할 때의 문제

- 행동하지 않거나 예외를 던지는 오버라이드 메서드 → 클라이언트 기대 충족 X, 행동 호환 X
- 클라이언트가 타입에 따라 분기처리 → 개방-폐쇄 원칙 위반

## 클라이언트의 기대에 따라 계층 분리하기

인터페이스 분리 원칙(Interface Segregation Principle, ISP): 인터페이스는 클라이언트가 기대하는 바에 따라 분리돼야 한다

- 주로 클라이언트 요구 변경에 따라 인터페이스 변경 → 변경 파급 효과 제어

자연어에 현혹되지 말고 요구사항 속에서 클라이언트가 기대하는 행동에 집중하라

- 현실 정확하게 묘사 X, 요구사항을 실용적으로 수용하는 것을 목표로

## 서브클래싱과 서브타이핑

서브클래싱(구현 상속, 클래스 상속): 코드 재사용 목적의 상속

- 행동 호환성, 대체 가능성 x

서브타이핑(인터페이스 상속): 타입 계층 구성 목적의 상속

- 행동 호환성, 대체 가능성 O
- 대체 가능함의 최소 조건: 서브 타입이 슈퍼 타입의 퍼블릭 인터페이스와 동일하거나 더 많은 오퍼레이션 포함해야 한다

행동 호환성과 대체 가능성은 상속 관계 구축을 위해 따라야 할 지침

# 04 리스코프 치환 원칙

리스코프 치환 원칙(Liskov Substitution Principle, LSP): 서브 타입은 기반 타입에 대해 대체 가능해야 한다

- 기반 타입 인터페이스가 서브 타입으로 치환되어도 클라이언트가 차이점 인식 못해야 한다(클라이언트 동작은 변하지 않아야 한다)

## 클라이언트와 대체 가능성

대체 가능성을 결정하는 것은 클라이언트다

- 어떤 모델의 유효성은 클라이언트 관점에서만 검증 가능하다
- 클라이언트와 떨어진 채 가정한 모델은 클라이언트와 협력 관계 속에서 잘못됨을 깨닫게 된다

## is-a 관계 다시 살펴보기

is-a 관계를 타입 네이밍 가이드로 생각해보라

- 클라이언트 입장에서 행동이 호환된다면, is-a로 연결해도 어색하지 않은 단어로 네이밍하라
- 서브타이핑을 위해 상속 사용할 때만 is-a 관계이다

## 리스코프 치환 원칙은 유연한 설계의 기반이다

리스코프 치환 원칙은 개방-폐쇄 원칙 만족의 전제 조건

- 리스코프 치환 원칙 만족 → 클라이언트 수정 없이 자식 클래스 추가로 기능 확장 가능
- 리스코프 치환 원칙 위반 → 잠재적인 개방-폐쇄 원칙 위반

## 타입 계층과 리스코프 치환 원칙

타입 계층 구현 시에는 리스코프 치환 원칙을 준수해야

- 상속은 구현의 한 방법일 뿐

# 05 계약에 의한 설계와 서브타이핑

계약에 의한 설계(Design By Contract, DBC): 클라이언트-서버 사이 협력을 의무(obligation)와 이익(benefit)으로 구성된 계약 관점에서 표현하는 것

- 리스코프 치환 원칙: 서브 타입은 클라이언트와 슈퍼 타입 간의 계약을 준수해야 한다

DBC의 구성 요소

- 사전 조건(precondition): 클라이언트가 정상적인 메서드 실행 위해 만족시켜야 하는 조건
- 사후 조건(postcondition): 메서드 실행 후 서버가 클라이언트에게 보장해야 하는 조건
- 클래스 불변식(class invariant): 메서드 실행 전, 후에 인스턴스가 만족시켜야 하는 조건

## 서브타입과 계약

클라이언트 관점에서의 대체 가능성을 위한 제약

- 서브타입에 더 강력한 사전 조건을 추가할 수 없다
- 서브타입에 슈퍼타입과 같거나 더 강한 사후조건을 정의할 수 있다
- 서브타입에 더 약한 사후조건을 정의할 수 없다
