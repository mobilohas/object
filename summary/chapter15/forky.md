# 01 디자인 패턴과 설계 재사용

## 소프트웨어 패턴

패턴이란

- 반복적으로 발생하는 문제 + 해법 쌍
- 패턴을 통해 이미 알려진 문제와 해법을 문서화하고 이로 다른 사람과 의사소통
- 추상적 원칙과 실제 구현 사이 간극을 메워 실제 코드 작성 도움
- 요점은 실무에서 탄생했다는 것

패턴: 하나의 실무 컨텍스트에서 유용하게 사용해왔으며 다른 실무 컨텍스트에서도 유용할것으로 예상되는 아이디어

- 경험을 통해 축적된 실무 지식을 효과적으로 요약, 전달
- 커뮤니티가 공유할 수 있는 어휘집 제공

패턴 언어, 패턴 시스템: 연관된 패턴들의 집합이 모여 구성

- 연관된 패턴 카테고리 + 패턴의 생성 규칙 + 한 패턴 언어 내의 다른 패턴과의 관계 및 협력 규칙

## 패턴 분류

### 아키텍처 패턴

- 상위 패턴
- 미리 정의된 서브시스템과 각 책임 + 서브시스템들 간 관계 조직화하는 규칙 및 가이드라인 → 소프트웨어의 전체적인 아키텍처 템플릿
- 언어, 패러다임 독립적

### 디자인 패턴

- 중규모 패턴
- 협력 컴포넌트 사이에 반복적으로 발생하는 구조 → 특정한 설계 문제 해결
- 언어, 패러다임 독립적

### 이디엄

- 하위 패턴(특정 측면 구현 방법 서술)
- 특정 언어 기능 활용 → 컴포넌트 또는 컴포넌트 간 특정 측면 구현
- 언어 종속적

### 분석 패턴

- 나머지 셋과 달리 기술적인 문제보다 도메인 개념적인 문제 해결
- 업무 모델링 시 발견되는 공통적인 구조 표현하는 개념들의 집합

## 패턴과 책임-주도 설계

책임 협력 시의 어려움들

- 어떤 책임이 필요한가?
- 책임을 어떤 객체에게 할당할까?
- 객체와 객체 간 어떤 의존성이 존재해야 할까?

패턴은 공통적으로 사용할 수 있는 역할, 책임, 협력의 템플릿

- 특정 상황에 적용할 설계를 쉽고 빠르게 떠올릴 수 있다
- 단지 역할, 책임, 협력 템플릿만 제공할 뿐 구체적인 구현방법을 제한하지 않는다

## 캡슐화와 디자인 패턴

대부분 디자인 패턴의 목적 = 특정 변경 캡슐화 → 유연, 일관성 있는 협력 설계 공유

- 중요한 것은 구현 방법 또는 구조가 아니다
- 어떤 변경을 캡슐화하는지, 이를 위해 어떤 방법을 사용하는지가 중요

## 패턴은 출발점이다

패턴이 설계 목표가 되면 안된다

- 패턴은 `복잡성의 가치 > 단순성의 가치`일 때만 정당화돼야
- 동료들이 패턴에 익숙한지 확인 후, 그렇지 않다면 패턴에 대한 지식도 공유해야

패턴은 출발점이다

- 패턴이 현재 문제에 딱 들어맞지 않더라도 참조할 수 있는 좋은 모범
- 우리가 직면한 문제를 분석하고, 창의력 발휘하여 적절히 수정해라

# 02 프레임워크와 코드 재사용

### 코드 재사용 대 설계 재사용

설계 재사용보다 더 좋은 방법은 코드 재사용

- 설계 재사용 → 매번 언어 특성에 맞게 가공, 코드 재작성
- 코드 재사용 → 별도 프로그래밍 없이 컴포넌트 조립으로 애플리케이션 구축

그러나 비현실적

- 서로 다른 문제에서 일반화될 수 있는 부분은 국소적
- 다양한 도메인에서 재사용되는 컴포넌트는 비현실적

프레임워크 = 설계 재사용 + 코드 반복 피하는 객체지향 진영의 방법

- 구조 - 추상 클래스나 인터페이스 정의하고 인스턴스 사이의 상호작용을 통해 시스템 전체 또는 일부를 구현해 놓은 재사용 가능한 설계
- 사용 목적 - 개발자가 현재 요구사항에 맞게 커스터마이징할 수 있는 애플리케이션 skeleton
    - 코드 재사용을 통해 설계 자체를 재사용하는 것이 주 목적

## 상위 정책과 하위 정책으로 패키지 분리하기

상위 정책을 다양한 상황에서 재사용할 수 있어야 한다

- 상위 정책에 속하는 역할들의 협력은 변하지 않는다
- 세부사항은 변한다

변하는 부분과 변하지 않는 부분을 분리해야 한다

- 별도의 패키지로 분리하는 것으로 시작
- 세부 사항 패키지는 항상 상위 정책 패키지에 의존해야 한다

프레임워크 → 여러 애플리케이션에 걸쳐 일관성 있는 협력 구현할 수 있게 해준다

- 재사용 가능한 상위 정책 제공 → 다양한 애플리케이션에 걸쳐 일관성 있는 협력 제공

## 제어 역전 원리

훌륭한 객체지향 설계 = 의존성이 역전된 설계

- 의존성이 역전되어 있지 않다 → 사용한 언어와 무관하게 절차적 설계인 것

제어 역전(Inversion of Control), 할리우드 원리: 의존성을 역전시키면 제어 흐름의 주체 역시 역전된다

- 전통적인 구조 → 상위 정책 코드가 하부의 구체 코드 호출 (애플리케이션이 라이브러리 호출)
- 의존성 역전 구조 → 프레임워크가 애플리케이션에 속한 서브 클래스 호출(프레임워크가 제어 흐름의 주체)

협력을 제어하는 것은 프레임워크

- 할리우드 캐스팅 담당자 “연락하지 마세요. 저희가 연락하겠습니다.”
- 개발자의 코드가 프레임워크를 호출하지 않는다. 프레임워크가 개발자의 코드를 호출한다.
